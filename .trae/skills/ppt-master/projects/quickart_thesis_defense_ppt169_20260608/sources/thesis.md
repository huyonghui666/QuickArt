基于多模型融合与Flutter的跨平台AI内容生成系统设计与实现

摘要

生成式人工智能技术在图像与视频创作场景中发展得很快，移动端用户对多模态内容生成的需求也在持续增长。现有的AIGC应用普遍存在模型能力分散、创作流程割裂的问题，移动端的工程落地也相对复杂，本文正是针对这几个方面，设计并实现了一套把多模型融合与Flutter结合起来的跨平台AI内容生成系统。

客户端这边用Flutter来构建，把Riverpod与GoRouter引入进来，分别负责复杂状态的管理和页面路由的协同；服务端那边则基于Spring Boot 3与Kotlin搭建，把多个模型的调用接口统一封装了起来，长耗时生成任务的状态同步问题，是通过异步任务队列、轮询与WebSocket推送这三种机制组合来解决的。核心业务层面，文生图、图生文、图生视频、AI换脸这几项功能都已实现，工作室管理、结果弹窗与下载到相册也一并提供了。从测试结果来看，功能完整性与交互流畅性都有不错的表现，移动端AIGC创作的实际需求基本上能够得到满足。本文的工作，为多模型能力在跨平台移动应用中的工程化落地提供了一些可复用的设计思路与实践参考。

关键词：跨平台开发；Flutter；多模型融合；AIGC；端云协同；WebSocket

__Design and Implementation of a Cross\-Platform AI Content Generation System Based on Multi\-Model Fusion and Flutter__

__ABSTRACT__

Generative artificial intelligence has been advancing rapidly in image and video creation, and mobile users' demand for multimodal content generation keeps growing as a result\. A closer look at existing AIGC applications reveals several recurring issues: model capabilities tend to be scattered across separate tools, creation workflows are fragmented, and getting these systems to run well on mobile devices is far from straightforward\. To tackle these challenges, this paper presents the design and implementation of a cross\-platform AI content generation system that brings together multi\-model fusion and Flutter\.

On the client side, Flutter serves as the development framework, with Riverpod handling complex state management and GoRouter taking care of coordinated page routing\. The server side runs on Spring Boot 3 and Kotlin, where multiple model invocation interfaces have been wrapped into a unified layer; for long\-running generation tasks, status synchronization is achieved through a combination of asynchronous task queues, polling, and WebSocket push\. The core feature set covers text\-to\-image, image\-to\-text, image\-to\-video, and AI face swapping, while studio management, result pop\-up display, and cross\-platform sharing have also been built in\. Testing shows the system holds up well in both functional completeness and interaction smoothness, meeting the practical needs of mobile AIGC creation\. The work carried out in this paper offers a reusable architectural approach and hands\-on reference for engineering multi\-model capabilities into cross\-platform mobile applications\.

__Key words：__cross\-platform development; Flutter; multi\-model fusion; AIGC;  end\-cloud collaboration; WebSocket

<a id="_Toc8149"></a><a id="_Toc30970"></a><a id="_Toc28112"></a><a id="_Toc24628"></a>1\.1研究背景与意义

生成式人工智能已经不再只是做文本生成了，它正在逐步走向图像、视频等多模态协同生成的方向，这条技术演进路径也被研究者们普遍视为迈向更高通用智能能力的重要一步\[1\]。从产业侧来看，大模型相关技术体系与行业应用场景都在持续扩展，AIGC这件事也正在把重心从概念验证阶段往工程化落地阶段转移\[2\]；尤其是视频生成这个方向，行业观察普遍指出它的应用价值已经有了从"演示型能力"向"生产力工具"转化的明显趋势\[3\]。

移动互联网用户对"随时创作、即时分享"的需求也一直在提升，这在客观上推动着AIGC能力向移动端迁移，但现有的应用在这方面做得并不理想——模型能力比较分散，创作流程割裂，端侧状态协同也相当复杂，用户很难从中获得一套高质量的一体化创作体验，所以围绕跨平台移动端来构建一个可扩展的多模型融合系统，是有明确现实需求和研究价值的。

本研究的意义可以从三个方面来理解：一是应用意义，把文生图、图生图、图生视频与AI换脸等能力统一整合到一起，用户就不需要在多个应用之间来回切换了，移动端AIGC创作的效率也能因此得到提升；二是工程意义，针对AIGC场景中长耗时任务、异步状态同步与多页面协同这几个问题，本文探索了一套可复用的端云协同实现方案；三是社会与治理意义，AIGC在赋能内容生产的同时也带来了内容真实性、叙事偏差与使用边界等方面的风险，把"可用性"与"规范性"一并纳入设计过程，是系统化工程实践能够发挥作用的地方\[4\]。

<a id="_Toc6799"></a><a id="_Toc6492"></a><a id="_Toc10717"></a><a id="_Toc7437"></a><a id="_Toc19908"></a><a id="_Toc30154"></a>1\.2国内外研究现状

国内研究现状

国内关于AIGC的研究与应用，目前主要集中在以下五个方向上。

一是生成式大模型能力演进与应用外延。相关研究指出生成式模型正在从单轮内容生成往任务化、系统化应用的方向发展，应用边界也在持续扩展；在此基础上，AI智能体技术被进一步提出来作为大模型应用落地的重要路径，强调的是"模型能力 \+ 任务编排 \+ 业务闭环"这种融合趋势\[5\]。国内头部大模型平台已经把多模态生成能力以标准化API的形式对外开放了，日均调用量突破了数十万亿次\[6\]，这标志着大模型服务正在从研究阶段全面进入工程化规模应用阶段。

二是图像与视频生成技术研究。以扩散模型为代表的生成式图像技术近年来取得了突破性进展，Ho等人提出的去噪扩散概率模型（DDPM）\[7\]奠定了扩散模型的理论基础，Rombach等人进一步提出了潜在扩散模型（LDM）\[8\]，把扩散过程放到压缩的潜在空间中来执行，在大幅降低计算成本的同时实现了高分辨率图像生成，成为当前主流文生图系统的核心技术路线。国内研究在此基础上积极探索模型微调、风格迁移与提示词工程等应用层优化方向，推动了AIGC图像生成能力在移动端场景的落地。

三是多模态交互与行业应用深化。围绕文本、图像、语音等多模态融合，国内综述研究已经把其关键技术与发展方向做了系统性分析\[9\]；在产业侧，AIGC正在向更强的生产属性转变，视频相关能力尤其明显，它正在从体验型工具往内容生产工具迁移，并在大规模调用场景下验证了云端模型服务的可用性与稳定性。

四是工程平台与系统架构研究。针对企业级落地需求，国内研究逐步把重心放到了AI平台的统一能力封装、接口治理和服务化设计上\[10\]；在推理执行层面，任务调度、并发控制和状态回传机制被证明是提升系统吞吐与可靠性的关键因素\[11\]。

五是跨平台移动应用开发。Flutter是Google推出的跨平台UI框架，凭借自绘渲染引擎与Dart语言的组合，在移动端开发领域得到了广泛关注与应用\[12\]\[13\]；国内开发者社区围绕Flutter的状态管理、性能优化与工程实践积累了丰富经验，相关技术书籍与实践案例为跨平台AIGC应用的客户端工程化实现提供了重要参考。

国外研究现状

国外研究更强调方法创新与交互范式扩展，主要体现在以下四个方面。

第一个方面是生成式模型的理论基础研究。Vaswani等人提出的Transformer架构\[14\]通过自注意力机制实现了对序列数据的高效建模，成为当前大语言模型与多模态生成模型的核心组件；Ho等人基于此提出了DDPM，Rombach等人进一步把扩散过程迁移到了潜在空间，推动了文本到图像、文本到视频等跨模态生成能力的快速发展，也为本系统所接入的云端生成模型提供了理论支撑。

第二个方面是视觉\-语言协同驱动的复杂任务处理。相关工作已经把视觉语言模型用到了交互式视频理解与检索代理上，体现出多模态模型在视频场景中的任务化潜力\[15\]，这一方向的研究为本系统图生文、图生视频等功能的设计提供了参考依据。

第三个方面是生成式AI与多模态用户界面融合。研究已经把跨平台适配问题纳入多模态交互框架，指出在不同终端维持一致体验、低延迟反馈与可解释交互将成为下一阶段智能应用落地的重点\[16\]，这与本系统在Flutter跨平台框架下构建统一交互体验的工程目标是高度契合的。

第四个方面是软件工程架构与后端服务研究。Martin提出的Clean Architecture\[17\]强调依赖倒置与关注点分离原则，为复杂移动应用的分层架构设计提供了理论指导；Newman在微服务领域的系统性研究\[18\]则为后端服务的模块化组织与独立部署提供了实践参考，本系统服务端的功能模块划分与接口设计都参考了上述架构思想。

综合国内外研究来看，国内在平台化与工程化落地方面积累较多，图像与视频生成技术的应用探索也比较活跃；国外在生成模型理论基础与多模态交互范式上探索更深，架构设计方法论也更为成熟。不过当前研究仍然缺少一套面向移动端场景、能够同时覆盖"多模型融合、跨平台交付、异步任务协同与业务闭环"的系统化实现方案，本文的工作正是在上述研究基础上，针对移动端AIGC应用的工程化落地问题展开探索的。

<a id="_Toc22011"></a><a id="_Toc2342"></a><a id="_Toc30390"></a><a id="_Toc12491"></a>2\.1 客户端技术

<a id="_Toc2035"></a><a id="_Toc25792"></a><a id="_Toc19114"></a><a id="_Toc13370"></a>2\.1\.1 Flutter

Flutter 是 Google 推出的一款开源跨平台 UI 开发框架，底层用 Dart 语言来构建，和 React Native 这类依赖原生组件桥接的方案有所不同——Flutter 是直接通过底层 Skia/Impeller 渲染引擎来绘制界面的，不需要依赖各平台的原生控件，所以 Android 与 iOS 双端的界面能做到高度一致。Flutter 把界面拆分成可复用的 Widget 树，开发者通过组合的方式来构建复杂页面，代码结构清晰，维护起来也比较方便；框架本身内置了丰富的 Material Design 与 Cupertino 风格组件，同时也支持自定义渲染，各种 UI 设计需求基本上都能满足。性能方面，Flutter 的渲染路径比较短，帧率也比较稳定，在动画流畅度与多媒体展示这类场景下表现突出，用来构建高交互性的移动端应用是很合适的。

<a id="_Toc7798"></a><a id="_Toc31425"></a><a id="_Toc13783"></a><a id="_Toc4420"></a>2\.1\.2 SQLite

SQLite 是一款轻量级的嵌入式关系型数据库管理系统，由 D\. Richard Hipp 开发并以公有领域方式开源发布。SQLite 无需独立的服务器进程，整个数据库以单一文件形式存储于本地磁盘，具有零配置、自包含、跨平台等特点。它支持标准 SQL 语法，提供完整的事务支持（ACID），在数据完整性与并发读写方面表现可靠。SQLite 体积极小，资源占用低，广泛应用于移动端、嵌入式设备及桌面应用的本地数据持久化场景，是目前全球部署量最大的数据库引擎之一。

2\.1\.3 Hive

Hive 是专门为 Flutter 与 Dart 设计的一款轻量级本地键值存储库，完全基于纯 Dart 实现，不需要依赖任何原生代码；它把数据以二进制格式存到本地文件里，读写速度很快，在性能测试中，简单键值读写场景下的表现要明显优于 SQLite 这类关系型方案。Hive 支持强类型数据存储，通过 TypeAdapter 机制能把自定义的 Dart 对象直接序列化持久化，用起来简洁直观，上手成本不高。另外 Hive 还提供了加密 Box 功能，可以把敏感数据用 AES\-256 加密后再存储，有本地数据安全保护需求的应用场景用这个是比较合适的。

2\.2 服务端技术

<a id="_Toc94"></a><a id="_Toc3782"></a><a id="_Toc9965"></a><a id="_Toc26808"></a>2\.2\.1 Spring Boot 3

Spring Boot 是在 Spring 框架基础上构建的一款开源 Java 应用开发框架，它把"约定优于配置"的设计理念贯彻得比较彻底，搭建和部署 Spring 应用的流程因此得到了大幅简化；开发者不需要写大量 XML 配置，只要把对应的 Starter 依赖引入进来，Web、安全、数据访问这些能力就能快速集成进去了。Spring Boot 3 以 Spring 6\.0 为基础，对运行环境的要求是 Java 17 及以上版本，命名空间这边也全面切换到了 Jakarta EE，同时还把对 GraalVM 原生镜像编译的支持加了进来，应用可以提前编译成原生二进制文件，启动速度能得到显著提升，运行时的内存占用也能降下来，对云原生部署场景的适应性更好了\[19\]。

<a id="_Toc23985"></a><a id="_Toc10648"></a><a id="_Toc22766"></a><a id="_Toc26983"></a>2\.2\.2 Kotlin

Kotlin 是 JetBrains 推出的一门静态类型编程语言，跑在 JVM 上，和 Java 能完全互操作；语法层面，它把空安全机制、扩展函数、数据类、Lambda 表达式、智能类型转换这些现代语言特性都提供了，样板代码因此能减少不少，代码的可读性与健壮性也能得到提升。协程机制是 Kotlin 在异步编程上的一个亮点，它提供了一套轻量高效的并发模型，资源消耗比传统线程方案要低，代码结构也更接近同步写法，理解和维护起来都比较方便。2017 年 Google 把 Kotlin 列为 Android 官方开发语言之后，它在服务端开发领域也慢慢得到了广泛应用，Spring 框架对 Kotlin 的支持也做得比较深入。

<a id="_Toc15781"></a><a id="_Toc2357"></a><a id="_Toc17649"></a><a id="_Toc27411"></a>2\.2\.3 PostgreSQL

PostgreSQL 是一款开源的对象关系型数据库管理系统，功能比较全面，遵循 SQL 标准，复杂查询、外键、触发器、视图、事务完整性（ACID）以及多版本并发控制（MVCC）这些特性它都有；数据类型方面也很丰富，除了标准类型之外，JSON、数组、范围类型、全文检索这些扩展能力也都支持，各种业务数据存储需求基本上都能覆盖到。它的稳定性与可靠性经过了数十年生产环境的验证，在高并发读写与大数据量场景下表现也比较优异，不少企业级应用都把它作为关系型数据库的首选方案。另外 PostgreSQL 采用的是宽松的开源许可证，不需要支付商业授权费用，这一点对于有成本控制需求的项目来说也是个不小的优势。

2\.2\.4 阿里云 OSS

阿里云对象存储服务（Object Storage Service，OSS）是阿里云推出的一项云端存储服务，在容量、安全性、成本和可靠性方面都有不错的表现；它以对象作为基本存储单元，任意类型的文件都能上传、下载和管理，标准、低频访问、归档等多种存储类型也都提供了，不同访问频率的需求基本上都能覆盖到。OSS 本身内置了 CDN 加速能力，通过自定义域名与签名 URL 就能把资源的访问控制做起来，数据安全方面有一定保障。SDK 这边覆盖了主流编程语言，接入起来不复杂，图片、音视频、文档这类非结构化数据存到 OSS 里是比较合适的，在国内云端文件存储的技术选型中也是用得比较多的方案之一。

<a id="_Toc7881"></a><a id="_Toc5934"></a><a id="_Toc29690"></a><a id="_Toc29898"></a>2\.3 通信技术

<a id="_Toc23673"></a><a id="_Toc29658"></a><a id="_Toc1661"></a><a id="_Toc7247"></a>2\.3\.1 WebSocket

WebSocket 是 IETF 于 2011 年标准化的一项网络通信协议（RFC 6455），底层基于 TCP，能在客户端与服务端之间建立起全双工的持久连接；和传统 HTTP 请求\-响应模式不一样的地方在于，WebSocket 在握手阶段通过 HTTP 完成协议升级之后，双方就可以在同一条连接上随时互相发消息了，不需要反复建立连接，延迟低、开销也小。服务端需要主动往客户端推数据的场景，WebSocket 是比较适合的，实时消息通知、在线协作、数据监控这类需求都能用它来做；和长轮询方案比起来，WebSocket 把那些不必要的请求开销省掉了，服务端压力与网络带宽消耗都能因此降下来，在现代实时 Web 与移动应用里是用得比较多的通信方案\[20\]。

2\.4 开发工具

<a id="_Toc30150"></a><a id="_Toc15014"></a><a id="_Toc23778"></a><a id="_Toc10359"></a>2\.4\.1 Android Studio

Android Studio 是 Google 基于 IntelliJ IDEA 平台推出的官方 Android 集成开发环境（IDE），2013 年正式发布之后逐步把 Eclipse 取代了，成为 Android 开发的标准工具；它内置了 Flutter 与 Dart 插件支持，代码补全、语法高亮、实时错误检测、Widget 预览与热重载这些功能都有，Flutter 应用的开发效率因此能得到不小的提升。内置的 Android 模拟器支持多种设备型号与系统版本的模拟运行，开发者在不同环境下做调试和测试都比较方便；Gradle 构建系统、版本控制工具与性能分析器也都集成进来了，从编码、构建、调试到性能优化这一整套开发流程基本上都能覆盖到，在 Flutter 移动端开发里，Android Studio 是用得最多的 IDE 之一。

<a id="_Toc29673"></a><a id="_Toc20202"></a><a id="_Toc2306"></a><a id="_Toc16750"></a>2\.4\.2 IntelliJ IDEA

IntelliJ IDEA 是 JetBrains 公司开发的一款面向 JVM 生态的专业集成开发环境，在 Java 与 Kotlin 开发工具里，它的功能算是比较强大的，业界认可度也很高；智能代码补全、深度代码分析、重构辅助、数据库管理、HTTP 请求测试这些功能它都有，对 Spring Boot、Kotlin 协程、JPA 等技术栈的支持也做得比较深入，服务端开发效率能因此得到明显提升。内置的 Spring 初始化向导与 Bean 依赖图可视化功能也挺实用的，开发者可以用它快速把项目结构搭起来，组件之间的关系也能看得比较清楚。IntelliJ IDEA 分社区版和旗舰版两个版本，社区版免费开源，旗舰版需要商业授权，但 Spring、数据库与远程开发这些企业级功能都能完整用到，做 Spring Boot 服务端开发的话，旗舰版是用得比较多的选型工具。

<a id="_Toc27800"></a><a id="_Toc20703"></a><a id="_Toc7136"></a><a id="_Toc6408"></a>2\.5 本章小结

本章把系统开发所涉及的核心技术与工具做了一个系统性的介绍。客户端这边，Flutter 负责跨平台 UI 渲染，SQLite、Hive 与 SharedPreferences 分别把结构化数据、对象数据与轻量配置的本地持久化需求给覆盖了；服务端那边，Spring Boot 3 与 Kotlin 构成了后端业务开发的核心框架，关系型数据的可靠存储交给 PostgreSQL 来做，图片与视频这类非结构化文件的云端管理则由阿里云 OSS 负责；通信层面，WebSocket 协议把服务端向客户端实时推送消息这件事给支撑起来了；开发工具方面，Android Studio 与 IntelliJ IDEA 分别为客户端和服务端开发提供了集成开发环境，两边的开发效率都有保障。

根据业务流程分析，本系统面向普通用户提供服务，功能模块划分为：认证登录模块、QuickArt创作模块、工具模块、工作室模块与个人设置模块。系统总体用例如图3\-2所示。

3\.2\.1 认证登录模块

认证登录模块负责把用户身份的验证与管理这块工作承担起来。系统采用的是第三方社交账号授权登录的方式，用户不需要手动注册，授权完成之后服务端会自动把用户信息创建好，同时把 JWT Token 签发出来；客户端在后续请求里带上这个 Token 就能完成身份校验了，Token 过期之后需要重新登录。该模块具体的功能需求有以下几点：一是支持第三方社交账号授权登录；二是登录成功后把 Token 持久化到本地，下次启动的时候能自动恢复登录状态；三是支持退出登录，退出时把本地用户数据一并清除掉。

3\.2\.2 QuickArt创作模块

QuickArt 创作模块是系统的核心功能模块，主要负责把多模态 AI 内容生成能力提供给用户。该模块具体的功能需求可以从以下几点来看：一是文生图，用户把文字提示词输入进去，选好艺术风格之后提交，系统就会把对应风格的图片生成出来；二是图生图，用户上传一张图片，输入提示词，系统对图片内容进行编辑生成出来；三是图片模板，系统提供了一批预设图片模板，用户选好模板之后就能快速把对应风格的图片内容生成出来；四是生成结果支持预览，也能保存到工作室里，还可以做跨平台分享/下载。

3\.2\.3 工具模块

工具模块负责把视频生成与 AI 换脸这类扩展创作能力提供给用户。该模块具体的功能需求有以下几点：一是文生视频，用户把提示词输入进去，系统就会把对应内容的短视频生成出来；二是图生视频（首尾帧），用户分别把首帧与尾帧图片上传上去，系统会把首尾衔接的过渡视频生成出来；三是视频模板，系统提供了一批预设视频模板，用户选好之后就能快速把对应风格的视频内容生成出来；四是 AI 换脸，用户先把目标图片上传上去，系统检测到图中的人脸之后，用户再选择替换用的脸源，换脸生成就能完成了。

3\.2\.4 工作室模块

工作室模块负责把用户历史生成任务的统一管理与展示这块工作承担起来。该模块具体的功能需求有以下几点：一是把用户所有的历史生成任务展示出来，任务类型、状态与生成结果都能看到；二是任务状态支持实时更新，处理中的任务完成之后会自动刷新，不需要用户手动操作；三是对生成结果可以做预览、下载与分享，操作起来比较方便；四是应用重启之后能从本地把任务列表恢复回来，数据的连续性有保障。

3\.2\.5 支付与积分模块

支付与积分模块负责把系统的商业化能力支撑起来。第三方支付平台已经成为移动应用商业化的重要基础设施了\[21\]，本系统把支付宝接入进来，把积分购买的业务闭环给打通了。该模块具体的功能需求有以下几点：一是把积分套餐列表展示出来，用户可以选择对应的套餐进行购买；二是支持用支付宝完成订单创建与支付流程；三是支付成功之后服务端通过异步回调把积分到账这件事处理掉；四是用户可以在首页随时查看当前的积分余额。

3\.2\.6 个人设置模块

个人设置模块负责把用户个人信息管理与系统配置这块能力提供出来。该模块具体的功能需求有以下两点：一是把用户头像、昵称展示出来，让用户能一眼看到自己的基本信息；二是支持中英文语言切换，切换之后全局界面的文字会同步更新，不需要重启应用。

<a id="_Toc16113"></a><a id="_Toc22785"></a><a id="_Toc20880"></a><a id="_Toc8252"></a>3\.3 系统非功能性需求分析

非功能性需求描述系统在质量属性方面的约束与目标，主要包括性能、可用性、安全性与可维护性四个方面。

3\.3\.1 性能需求

在正常网络环境下，普通接口的响应时间需要控制在2秒以内；AI生成任务这边因为要依赖云端模型推理，耗时会比较长，需要通过异步机制与实时推送来把用户等待过程中的交互流畅性保障好；客户端页面切换与动画渲染的帧率要稳定在60fps，视觉体验才能流畅。

3\.3\.2 可用性需求

系统需要有比较好的容错能力，网络中断或WebSocket断连之后能自动重连，未完成任务的订阅也能恢复回来；客户端遇到异常情况时要给出友好的错误提示，不能让用户看到白屏或者无响应的情况；系统支持中英文双语，不同语言的用户都能正常使用。

3\.3\.3 安全性需求

接口鉴权这块采用JWT机制\[22\]来做，所有业务接口都需要带上有效Token才能访问；用户敏感数据存到本地的时候需要做适当保护；支付流程需要通过服务端验签来确保金额与订单数据不会被客户端篡改；生成结果文件通过签名URL来做访问控制，防止被未授权访问到。

3\.3\.4 可维护性需求

客户端采用Clean Architecture分层架构，服务端按功能模块独立组织，各模块职责清晰、耦合度低，后续要扩展功能或者做迭代维护都比较方便；代码需要遵循统一规范，关键逻辑要有必要的注释，这样后续的维护成本才能降下来。

<a id="_Toc1562"></a><a id="_Toc20571"></a><a id="_Toc12400"></a><a id="_Toc15477"></a>3\.4 可行性分析

可行性分析是软件工程开发前期的重要环节，旨在从多个维度评估项目的立项价值与实施保障。本节从经济可行性与技术可行性两个方面对系统进行论证。

3\.4\.1 经济可行性

客户端开发这边，系统采用Flutter跨平台框架，把"一次编写，Android与iOS双端运行"这件事做到了，和针对双平台分别独立开发的方案比起来，人力成本与开发周期都能省下不少。服务端那边，Spring Boot 3与Kotlin构成了开发基础，所依赖的框架与数据库都是开源免费的方案，不需要花钱买商业软件授权。AI算力方面，系统没有选择去购置昂贵的GPU服务器做私有化部署，而是把云端大模型服务平台接入进来，按需调用、按量计费，用很低的试错成本就能用上业界领先的多模态生成能力。综合来看，本系统的开发与运维成本完全在个人开发者或小型团队能控制的范围内，经济可行性是比较高的。

3\.4\.2 技术可行性

<a id="_Toc17596"></a><a id="_Toc22903"></a><a id="_Toc22934"></a><a id="_Toc18413"></a>5\.1 认证登录模块实现

<a id="_Toc5252"></a><a id="_Toc26703"></a><a id="_Toc6970"></a>5\.1\.1 第三方授权登录实现

本系统这边采用了第三方社交账号授权登录的方式，整个OAuth授权流程都通过小拓聚合登录平台来完成，整体流程可以分成三个阶段，一是客户端请求登录URL，二是用户完成授权，三是服务端处理回调并把Token签发出去。

服务端收到登录URL请求后，会把包含登录类型与随机UUID的state参数生成出来并暂存到内存里，用于防止CSRF攻击；到了回调阶段，服务端先把state的有效性校验一遍，通过后再去小拓平台换取用户信息，把用户的创建或更新完成，同时把用户头像异步上传到阿里云OSS，最后把JWT Token签发出来返回给客户端。

客户端登录成功后会把JWT Token持久化到本地存储里，下次启动时系统自动把Token读取出来并注入到Dio请求头中，用户不需要重复登录；不过Token一旦过期或失效，系统就会跳转到登录页并把本地用户数据清除掉，账号安全方面有了保障。

<a id="_Toc20544"></a><a id="_Toc28045"></a><a id="_Toc27226"></a><a id="_Toc23235"></a>7\.1总结

本次毕业设计是在分析移动端AIGC应用现状的基础上展开的，最终把一个基于多模型融合与Flutter的跨平台AI内容生成系统设计并实现了出来。系统以Flutter作为客户端开发框架，以Spring Boot 3和Kotlin来构建服务端，把火山方舟、Magic Hour等云端大模型平台接入进来提供AI能力支撑；数据层面由PostgreSQL承担结构化数据存储管理，由阿里云OSS承担文件资源存储管理，同时通过WebSocket协议把生成任务的实时状态推送到客户端。功能上系统已经把文生图、图生文、图生视频、AI换脸等多模态内容生成能力做了出来，也配套实现了工作室任务管理、支付宝积分充值和跨平台分享等完整业务能力，基本能够满足移动端用户的智能创作需求。

经过系统功能测试后可以看到，各模块运行都比较正常，异步任务推送以及断线恢复机制表现得较为可靠；在开发过程中，也对Flutter跨平台框架里的状态管理与路由协同机制做了深入研究，对“异步任务队列 \+ WebSocket推送”在长耗时AI任务场景下的工程实践进行了探索，并积累了端云协同架构设计和多模型接入方面的实际经验，这些工作都为后续相关研究与开发打下了基础。

<a id="_Toc6886"></a><a id="_Toc6561"></a><a id="_Toc13418"></a><a id="_Toc2083"></a>7\.2展望

虽然本系统已经把预期功能实现了出来，不过受开发周期和个人技术水平限制，系统在一些方面仍有进一步优化空间。当前的用户鉴权机制还比较基础，Token管理也还没有把分布式缓存方案引入进来，所以在多实例部署场景下还需要继续完善；另外，AI生成内容的质量可控性目前更多依赖云端模型自身能力，提示词优化引导和生成参数精细调节功能还不够完善。

往后看，随着大模型技术持续演进、移动端算力不断提升，面向移动端的多模态AI内容生成应用会有更大的发展空间。在技术层面，一方面可以进一步引入模型适配器机制，让多模型动态接入更灵活、把新模型扩展的工程成本降下来；在产品层面，另一方面可以探索把个性化推荐算法与社区生态建设结合起来，提升平台的用户粘性和内容价值；在工程层面，还可以结合云原生部署方案来提升系统可用性与弹性伸缩能力。本文的研究工作也希望能够为跨平台AIGC系统的工程化落地提供一定参考与借鉴。
